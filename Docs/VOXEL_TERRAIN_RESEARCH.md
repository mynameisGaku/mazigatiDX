# ボクセル地形・モデルの破壊表現: 調査と将来計画

調査日: 2026-11-24。これは将来の機能候補であり、実装済みの機能や確定した性能を示すものではない。[ロードマップ](ROADMAP.md)の既存の段階を進めた後、試作と計測により採用方式と時期を決める。

## 公開資料から分かること

任天堂は、地形をボクセルと材質の組み合わせで制作し、壊した中身や材質に応じた変化を表現すること、制作ツールで編集・確認できることを説明している。CEDECの講演概要では、地形に加えて敵やNPCへの応用も紹介している。[任天堂の開発者インタビュー](https://www.nintendo.com/us/whatsnew/ask-the-developer-vol-19-donkey-kong-bananza-part-2/)・[CEDEC講演概要](https://cedec.cesa.or.jp/2026/timetable/detail/s69a7a41874204/)

CEDEC講演の報道によると、形状を決める密度、蓄積するダメージ、マテリアル、濡れを持ち、密度は0〜255で管理する。メッシュ生成にはDual Contouringと頂点を制御するベクトル情報を用い、滑らかな曲面と鋭い形状を扱う。見た目には三軸投影、材質境界の混合、テクスチャのまとめ、変化の少ない面の単純化を用いたと報じられている。これらは講演の二次報道であり、公開情報だけで全実装を特定できるわけではない。[CGWORLDのCEDEC講演レポート](https://cgworld.jp/article/202609-cedec-bananza02.html)

## 必要なデータと処理

- 形状を決める占有・密度・符号付き距離は候補として比較する。物理の質量密度、破壊までの耐久度、形状の密度は意味と単位を分ける。
- 材質IDから、表示材質、硬さ、破壊時の音・粒子、摩擦などを参照する。破壊度や濡れは独立した値にし、温度なども追加できる形を目指す。ビット幅・精度・混合数はゲームの要件と誤差を測って決める。
- 地形は小領域に分け、空・一様・詳細領域を必要に応じて保持する。全領域を常に展開すると解像度の3乗でメモリが増える。材質表、量子化、省略可能な値、距離別の詳細度、読み出し・退避を比較する。OpenVDBの疎な木構造は参考候補であり、導入や実行時の適性は未決定。[OpenVDBの構造](https://www.openvdb.org/documentation/doxygen/overview.html)
- 破壊や生成では変更範囲と隣接領域を記録し、必要な面、衝突形状、見た目だけ更新する。Dual Contouringと他方式を、鋭い角、穴、継ぎ目、更新時間で比較する。境界の隣接値と異なる詳細度間の接続を検査する。
- 生成はシードと設定を保存し、編集差分を順序付きで保存・再適用できるようにする。乱数、生成器とデータの版、座標、同時編集の順序を含めて再現性を確認する。

## 既存モデルの見た目とボクセル化

無傷部分には元のモデルと材質をそのまま使い、変更部分の内部形状をボクセルから再生成する構成を第一候補とする。元表面の切り抜きと生成面の境界が一致する仕組みが必要で、重複描画、隙間、影・深度の不一致を検査する。破断面は内部材質を使い、残った表面のUV・法線・接線・材質を維持する方法として、元三角形の参照や投影を試す。三軸投影は破断面の候補だが、元のUVの再現を保証しない。

変換時には内部・外部の判定、薄い部品、穴の開いたメッシュ、重なった面、透明や切り抜き材質、解像度不足を検出する。OpenVDBの符号付き距離への変換も閉じた表面を前提としている。[OpenVDB MeshToVolume](https://www.openvdb.org/documentation/doxygen/MeshToVolume_8h_source.html) 無傷の見た目を基準画像で比較し、破壊後は解像度による形状誤差と境界の品質を測る。スキン・モーフを伴う動くモデルは変形と破壊の座標の対応が必要で、静的モデルの後に別途実現性を検証する。

## 責務、並列処理、描画

ボクセルの状態・編集・生成はゲーム／ワールド側の機能として、描画APIから独立させる。アセット変換、表面生成、描画への受け渡し、既存物理への衝突形状の受け渡し、保存を分け、必要になるまで新しい共通subsystemを増やさない。プロジェクトの `IJobSystem` と既存のスレッド管理を優先し、GPU資源と同期の実装は各描画バックエンドが担当する。

更新は領域の版を付けた読み取り用スナップショットから並列に生成し、古い結果や破棄済み領域の結果を採用しない。編集、描画、物理の反映時点と遅延の許容を決め、同時更新・領域の境界・終了時の寿命を検証する。物理は既存のJolt連携を調べ、生成中も使える衝突形状と安全な交換時点を設計する。

GPU計算を使う場合は、入力・出力・寿命・計算と描画の依存を描画グラフに宣言し、利用者定義パスにも接続できる形を目指す。グラフが実際に提供する同期機能は実装時に確認し、未対応の非同期計算を前提にしない。Unreal EngineのRDGは資源依存、パス、非同期計算の参考になる。[EpicのRDG仕様](https://dev.epicgames.com/documentation/unreal-engine/render-dependency-graph-in-unreal-engine)

## 導入順と合格条件

1. 固定サイズの小さな地形で生成・編集・保存・衝突・CPU表面生成を試し、密度／材質／破壊度／濡れを可視化する。単一スレッドを基準にする。
2. 小領域化とジョブ化を行い、境界、同時編集、古い結果の破棄、描画・物理の反映を検査する。メモリ、生成・更新時間、待ち時間を計測する。
3. 静的モデルの変換を加え、無傷画像と破断境界を検証する。未対応の入力と理由を制作時に表示する。
4. 大規模地形、読み出し、詳細度、GPU計算と描画パス、動くモデル、破片化を必要性と予算に応じて段階的に検討する。

全段階で、決定論、負座標、領域境界、穴と薄い面、各パラメータ、保存復元、並列更新、衝突と描画の版、終了処理を検査する。性能は代表シーンを定め、CPU・GPU時間、最大遅延、メモリ、転送量、更新領域数を計測してから目標を設定する。
